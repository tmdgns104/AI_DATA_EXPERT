# Notebook Output Style Contract V6.5

내부 분석은 엄격하게 하되 최종 Notebook은 사람이 데이터를 보면서 하나씩 판단한 흐름으로 보이게 작성한다.

- 원본 문제 셀은 그대로 보존한다.
- 처음부터 문제 유형을 단정하지 않는다. `데이터 확인 → 구조/시간축 확인 → 문제 유형 판단` 순서로 쓴다.
- 이상값이나 시간 오류는 `이상 발견 → 근거 확인 → 왜 수정하는지 설명 → 수정` 순서로 쓴다.
- EDA는 장식이 아니다. 자기상관, 분포, 그룹 구조 등에서 본 내용이 다음 split/baseline/입력 길이 선택의 근거로 이어져야 한다.
- `32개`, threshold, lag, feature set처럼 과제에서 정하지 않은 값은 최적값처럼 말하지 않고 `이번 실습에서 정한 조건`이라고 쓴다.
- 데이터로 비교 가능한 선택이면 Validation에서 후보를 비교한다.
- Validation은 모델/조건을 선택하는 근거로 사용하고, 최종 결론은 Test 결과를 중심으로 쓴다.
- 여러 지표가 엇갈리면 그대로 쓴다. 예: RMSE는 LSTM, MAE는 SimpleRNN이 더 좋을 수 있음.
- 모델 파라미터 수가 다르면 `같은 hidden size와 학습 조건에서 비교` 정도로 표현하고 `동일 복잡도`라고 과장하지 않는다.
- 기준모델과 복잡한 모델을 같이 비교한다. 기준모델이 이기면 그대로 결과로 인정한다.
- 내부 `DataGuard`, `Argument Ledger`, `Evidence ID`, `Verifier`, `final status: REVIEW` 같은 용어는 최종 Notebook에서 숨긴다.
- `rolling-origin backtest` 같은 전문 용어가 꼭 필요하지 않으면 `여러 기간으로 나눠 반복 확인`처럼 자연스럽게 쓴다.
- Markdown은 꼭 필요한 부분만 사용하고 한 블록은 짧게 유지한다.
- 코드만 봐도 알 수 있는 주석은 쓰지 않는다. 주석은 `왜` 그렇게 했는지 필요할 때만 짧게 쓴다.
- 자연스러운 한국어를 사용한다. `확인해봄`, `정했음`, `비교했음`, `크다고 보기는 어려움` 같은 표현을 허용한다.
- 결론은 `결과 → 차이의 크기 → 기준모델 대비 개선 → 조건/한계` 순서로 간결하게 쓴다.
